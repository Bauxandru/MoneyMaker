[2026-04-17] SAFETY: Added MAX_MARKET_EXPOSURE_USD per-market exposure cap (default 2× TRADE_USD = $20 at $10 budget, $14 at current $7). Block opening new arbs on a kalTicker where the bot has already committed ≥ cap in $ (sum of kalCost + pmCost + hedgeCost across every bot trade on that ticker regardless of status). Short-circuits both executeArb (ttExecution.ts, near sizing block at line 365) and executeArb3Leg (near sizing block at line 1997) BEFORE any order placement, with `abort-safety:market-exposure-cap` metric. Motivation: Arsenal EPL totals market accumulated ~77 PM Over + 16 KAL YES across many Dir-A/C fires creating ~$57 of naked-side exposure while existing guards (sessionSkipSet seeded at startup, TRADE_COOLDOWN_MS 60s) failed to catch compound stacking within one session. Cap is dollar-based, so it works uniformly across high/low-priced markets. Set `MAX_MARKET_EXPOSURE_USD=0` to disable. Configuration Reference table updated in CLAUDE.md. (src/ARB/ttConfig.ts, src/ARB/ttExecution.ts, CLAUDE.md)

[2026-04-17] SAFETY: Added dedup guard before PM GTC complete placement in runHedgeCycle. CRITICAL bug found in prod: the hedge cycle placed a NEW `placePmGTCBid` every cycle that satisfied the base conditions (pmViable + not-in-crossbook-cooldown), WITHOUT checking whether an active PM complete order already existed. Compare to the IOC sweep guard at ttHedge.ts:2307 which correctly skips when `hasActivePmCompleteKH`. User's PM open-orders UI showed 5 duplicate Gen.G GTC orders, 4 duplicate JD Gaming orders, 2 duplicate Arsenal orders — each for the FULL share count. If the book had ticked down, the bot would have over-hedged by 4-5× and burned capital. Fixed both the KAL-held branch (ttHedge.ts:2408) and PM-held branch (ttHedge.ts:1906): now compute `hasActivePmComplete` from `activeOrders` and add it as a negating condition in the placement guard. Also logs "PM complete GTC already active — skipping new placement (dedup guard)" once per minute per position so the skip is visible. (src/ARB/ttHedge.ts)

[2026-04-17] PERF: On-chain balance 2s TTL cache + 60s log throttle. Every runHedgeCycle tick was firing `getOnChainBalanceWithFallback` (hot path, ttHedge.ts:2031) AND `getOnChainBalance` in `capPmOrderByOnChain` for each held position, burning ~10 RPC calls/sec on idle positions (user's log showed `[HEDGE] On-chain balance: 0x Gen.G` / `5x Team Liquid` repeating every ~180ms cycle, plus "Capping order 7 -> 2" warning every cycle). Added module-level cache `_onChainBalCache` (keyed by tokenId, 2s TTL) transparently wrapping the calls; plus throttled log helpers (`logOnChainBalanceThrottled`, `cap:…` key) that only emit when the value or decision CHANGES, or at 60s intervals per token. Expected: ~90% RPC reduction during idle-market hedging, plus dramatically quieter logs. Fresh fills still detected promptly — 2s lag on RPC is below hedge-cycle reaction time. (src/ARB/ttHedge.ts)

[2026-04-17] FIX: Dashboard audit + stats now merge remote-bot (VPS) ingested trades with the local journal before comparing against exchange fills. Previously `runAudit()` at dashboard.ts:742 and `/api/stats` at dashboard.ts:1223 both called `loadTrades()` — which reads ONLY the local `data/arb_trades.json` and ignores the in-memory `remoteUsers` Map populated by `/api/ingest` POSTs from VPS bots. Both now do the same dedup-merge as `/api/trades`, so audit results and stats match the user's Total tab. Diagnosed after seeing 76 untracked-kal-fills warnings on legit tickers that were verified present in VPS arb_trades.json. (src/dashboard.ts)
